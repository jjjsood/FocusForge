# Brush preview (editor mode)
Reach: open a folder and fuse it (`--open`, `--fuse-tabs 0`, `--enter-editor`), answer **Keep**, and turn on **Preview** in the editor toolbar (`FFEditorToolbar::preview-switch`, or **Press p**). With the switch on, the brush ring of the Composite shows the selected source frame inside it while the pointer rests on an image point. The switch is one setting for the whole window: every tab shows the same state.
Sub-features: the **Preview** switch and the p key, the switch state shared by both tabs, the preview following the pointer over the Composite and, mirrored, over the frame pane, the preview hidden outside the image and while **Pipette** is armed, the preview in the Composite's own window, a hover that changes nothing (Undo, Redo and **Save checkpoint** stay greyed out, the export dialog still says "Exporting the unsaved fuse result held in this tab."), a stroke, undo and redo with the switch on, the switch off again.
Ids: `FFEditorToolbar::preview-switch` (the click; `buttons AppWindow::editor-toolbar` lists it as **Preview** on `FFToggle::area` with checked=true|false), `FFBrushCursor::preview` (the preview itself), `FFCanvas::pane-right` (the Composite), `FFCanvas::pane-left` (the frame pane), `FFEditorToolbar::pipette`, `FFEditorToolbar::undo`, `FFEditorToolbar::redo`, `FFTab::area` N, `FFUndockControl::area` 1 (undock the Composite) and 0 (dock it, in the second window), `ComparisonWindow::input` (the second window's pane), `FFCheckpointPanel::checkpoint-export`, `AppWindow::divergence-warning`.
Gotchas:
- Presence is not visibility. `FFBrushCursor::preview` is in the tree exactly while a preview picture is set, and the driver reads that: `shot <png> --crop FFBrushCursor::preview` writes a picture when it exists and reports `0 elements with id 'FFBrushCursor::preview'` when it does not. The element stays while its brush ring is hidden (the pointer left the panes), so a crop picture with no ring in a full-window shot means the pointer moved away, not that the preview is missing. A driven step reads presence only; colours and pixels are never compared. The driver's hover leaves the ring on screen after it releases, so a full-window shot shows the ring where the pointer was put.
- The repaint trap. A click on the **Preview** switch or on **Pipette** changes the switch or the pipette state at once but not the preview: that follows at the next pointer move over a pane. **Press p** updates it at once. A step that reads presence follows a hover or a **Press p**, never a click on the toolbar alone.
- A hover is a real `Other`-button press at the point (`hover <id> [N] <x> <y>`). The canvas takes it as a move: it starts no stroke, adds no undo step, and does not consume the armed pipette. Over the second window's pane it moves no window.
- The preview needs an image point. In the 1200x700 window the frame pane is 422 x 608 at window point 64,92 and the Composite 422 x 608 at 502,92; the 512 x 512 image fills a pane's full width, so a point 4 px inside a pane corner (506,96) is outside the image and carries no preview, while 713,396 (the Composite's centre) and 608,290 lie on it. Hovering the frame pane puts the same preview on the Composite's ring; which of the two rings carries the picture is a look, human only.
- With the Composite in its own window, that window is `--window 1`; the main window then shows one pane, `FFCanvas::pane-left`, 860 px wide with its centre at 494,396. The second window's handle stays in `list_windows` after it is docked; a docked window is read as two panes in the main window.
- The Preview caption is hidden when the editor toolbar is narrower than 1068 px (a 1200 px window); the switch is then a bare knob. Read it by its accessible name **Preview** with `buttons AppWindow::editor-toolbar` (checked=true when on), never by a caption. **Preview** is `FFToggle::area` 0 in editor mode. The switch is off on a fresh settings folder. **Press p** does nothing in STACKING mode, which has no toolbar switch.
- The export dialog line changes to "Exporting your current unsaved retouch edits." after a stroke, so reading "Exporting the unsaved fuse result held in this tab." after all the hovering shows the preview made no edit.
- A stroke drag takes about 40 s on a debug build; read `buttons AppWindow::editor-toolbar` afterwards.
- The driver cannot reach four things, so they are `(human only)` steps: the mouse wheel (the MCP server has no wheel tool, so Ctrl+wheel source stepping with the preview following is by hand), a modifier held while hovering (`--hold` exists on `click-id` only, so Alt held over the Composite is by hand), the state during a stroke (`drag` is one press, move and release, so the preview held from the press until the stroke paints, gone while the button is down after that and back after the release is by hand) and a relaunch (a journey is one launch, so the switch still on after a restart with the same settings folder is by hand).
- Human only, no driver can read it: the preview's look (the selected frame at about 80 % over the result, a soft edge, the frame pane's ring alone with no second picture), on the hardware adapter and on the software adapter.
